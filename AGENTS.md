# AGENTS.md

Этот репозиторий — шаблон админ-узла и приёмки. Инструменты узла — Go
stdlib; стек продукта выбирает отдельный проект. Никаких npm, Node.js и
сторонних пакетов у узла.
Перед первой правкой прочитай `RULES.md` целиком: десять правил обязательны
на каждом шаге, цикл шага — семь ворот, закрытие задачи — по определению
готовности.

## Прецеденты — в архив

`AGENTS.md` — только действующие правила, 1–3 строки и ссылка. Истории
«что случилось и почему правило появилось» — в `docs/AGENTS-ARCHIVE.md`.
Бюджет `AGENTS.md` — 14 КБ; проверка `verify.py` (`agents-size`).
Новый прецедент — в архив; в правиле строка «разбор — архив, дата».
Старт новой сессии — по `docs/TO-AGENTS-ONBOARDING.md`.

## Сначала почта

Первое действие в любом ходе — проверить почту:

```powershell
powershell -File "C:\Users\User\Documents\deepseek-harness\default-workspace\firstVibeCodingProject\deploy\check.ps1" -Agent template-agent
```

Если ответ `PENDING` — прочитать `mailbox\inbox` и ответить в `outbox`
до основной работы. Если `EMPTY` — продолжать задачу.

## Расписания — по имени чата

Заголовок — `<агент>: что делает`; создавать только в своём чате.
Границы и примеры — `docs/SCHEDULES.md` (разбор — архив, 29.10).

## Три попытки — эскалация

Если фикстура, тест или дефект не чинится за три попытки — остановись и
напиши conductor. Не четвёртая попытка, не просьба владельцу переключить
режим, не молчание.

Формат report: `topic: escalation`, `kind: request`, `requires: none`,
пять пунктов:

1. что не работает — одна фраза;
2. три попытки: правка, команда, результат — по строке;
3. точный текст ошибки, не пересказ;
4. гипотеза: права / архитектура / своя ошибка — и почему;
5. что нужно от узла: проверка прав, правка правила, воспроизведение.

## Правило без проверки не действует

Карта `docs/RULES-TESTS.md`; `verify.py` → `rules-tests` (нет строки, файла,
теста — красный) и `rules-dupes` (одинаковые заголовки, корни ≥ 0.7).
Указание «сделать правило/тест» — в том же шаге; строка в
`docs/REQUESTS.md`, гейт `requests`.

## Проснулся — пересчитай долги

Пробуждение — не только «прочитать, что пришло», но и пересчитать
обязательства после писем, решений владельца, отчётов узла и чужих
коммитов; иначе реестр отстаёт.

1. Почта: `check.ps1 -Agent template-agent`, прочитать всё.
2. Понять, что новые данные меняют в работе.
3. Пересчитать `DEBTS.md` в том же шаге: добавить, снять, уточнить.
4. В report — `долги: +N / −M / изменено K` и строка на изменение; пусто —
   `долги: +0 / −0 / изменено 0 — новых обязательств нет, потому что …`.

Нельзя: не тронуть реестр, писать «долги: 0» без причины, держать
обязательства в голове, закрывать долг без проверки.

Пробуждение по расписанию при непустой доске закрывает минимум один долг —
живой проверкой, строкой в `docs/WAKE-LOG.md`; гейт `wake-debts` краснеет
без тега и доказательства.

## Каждый ответ закрывает долг

Пока в `DEBTS.md` есть открытые пункты, каждый ответ закрывает хотя бы один —
живой проверкой и удалением строки. В отчёте — `долги: −1 / +0 / изменено 0`
и строка снятого. Долгов нет — «долгов нет»; ноль при непустой доске —
нарушение. «Сделано» без проверки и «почти закрытые» не считаются.

## Доска долгов

Единый файл — `DEBTS.md` в корне. Разделы строго по порядку:

1. `## Открытые`
2. `## Отложено владельцем`
3. `## Ждём владельца`

Семь колонок: `# | Долг | Кому | Почему открыт | Что разблокирует |
Приоритет | С какой версии`.

- `Кому` заполняется всегда: `я`, `владелец`, `владелец (позже)`, для
  тега `N…` — `узел`.
- `D…` — мой долг; `W…` — задача владельца с заявкой; `L…` — отложено
  владельцем (только чат); `N…` — задача узла.
- Приоритет только `P0`/`P1`/`P2`; «Что разблокирует» не пустое.
- Раздела «Закрытые» нет: снятое удаляется, история в git.
- Проверка: `deploy/debt-check.py`; гейт `debt-board`.

## Долги в сообщении — с колонкой #

Любая таблица долгов в чате и письме начинается с `#`; без неё отчёт не
считается. Перед отправкой — `python3 deploy/debt-table.py` (семь колонок;
без долгов — строка `| — | долгов нет | ... |`).

## Обязательный старт сессии

Это условие начала работы, а не рекомендация. Нарушение = задача не начата.

1. Прочитай `RULES.md` **целиком**, не по диагонали и не только индекс.
2. До первой правки выведи таблицу ровно из десяти строк:

   | # | Правило | Как выполнено в этой задаче |
   | --- | --- | --- |
   | 1 | Чистый код, имена и уборка | ... |
   | ... | ... | ... |
   | 10 | Данные и секреты | ... |

3. В колонке «Как выполнено» — конкретный файл, команда, тест или
   «не применимо: причина». Общие слова «буду соблюдать» не принимаются.
4. Не редактируй файлы, пока таблица не выведена.
5. Сначала правила и тест, потом код. Если правило требует схемы или
   теста — они должны быть в плане до изменения.
6. Эти два отчёта обязательны в каждом новом чате/сеансе, даже если
   правила читались раньше.

## Обязательное закрытие

Перед словом «готово»:

1. Открой в `RULES.md` раздел `## Определение готовности`.
2. Выведи отчёт по каждому пункту:

   | Пункт DoD | Доказательство |
   | --- | --- |
   | ... | команда + результат, путь к тесту, CI run, diff, файл |

3. Доказательство — это вывод команды, зелёный тест, ссылка на CI run,
   diff или конкретный файл. «Сделано» без доказательства не считается.
4. Если пункт не выполнен — напиши «не готово» и что осталось. Не называй
   задачу готовой частично.
5. Минимум перед закрытием: `python verify.py` — зелёный; тесты — зелёные;
   `go run ./cmd/deadcode` — без находок; `python verify.py --close-task` —
   зелёный; SVG-схемы обновлены; запись в `JOURNAL.md` или `docs/adr/` есть;
   закрытый долг удалён из `docs/DEBT.md`.

## В чате — что не сделано

В каждом ответе в чате, где есть статус работы, показывай фронт работ:

| Сделано | Не сделано | Осталось |
| --- | --- | --- |
| ... | ... | ... |

- «Не сделано» — это конкретные пункты, блокеры и то, что не проверено.
- Если не сделано ничего — пиши `Не сделано: ничего`.
- Не заменяй это отчётом DoD: DoD — отдельно, по пунктам с доказательствами.
- Не скрывай блокер за словом «готово»: «готово» только при пустом
  столбце «Не сделано».
- Проверка: `python deploy/check-reply.py <файл ответа>` — свободный пункт
  или забытая строка доски краснеют, ответ не уходит.

Короткий индекс (полные формулировки и проверки — в `RULES.md`):

1. Чистый код, имена и уборка
2. Все новые фичи — в схемах
3. Тесты под каждую фичу
4. Ноль сторонних зависимостей у узла и инструментов
5. Схемы — источник истины
6. Микроблоки и ООП
7. Читать перед записью
8. Пять минут — стоп
9. Проверять живо
10. Данные и секреты

## Правило остановки

1. Одна и та же проверка падает **дважды** — третью попытку не делаешь.
2. Вместо третьей — файл `docs/acceptance/<дата>-blocked-<slug>.md`: что
   проверял, точный текст ошибки, что пробовал, чего не хватает/какое
   решение нужно.
3. После этого останавливаешься: не пушишь «на всякий случай», не меняешь
   проверку, не отключаешь правило.
4. Готово — не «issue закрыт». Готово = коммит в `review`, зелёная
   проверка, файл приёмки. Статус issue меняет администратор узла.
5. Не хватает данных/доступа/решения — тоже `blocked`-отчёт, а не серия
   догадок.

## Проверка — фикстурами

1. Дефект, найденный живым проектом, закрывается тестом в CI шаблона:
   фикстура → действие → ожидаемый результат. Без продукта, без имён,
   без доступа к чужому хосту.
2. В issue запрещены формулировки «проверим на реальном проекте»,
   «ждём переезд», «закроем, когда проект запустит».
3. Живой проект в issue — только источник: что сломалось и при каких
   условиях.
4. Если сценарий не воспроизводится на фикстуре — проверка сформулирована
   неверно: сначала переформулировать, потом кодить.
