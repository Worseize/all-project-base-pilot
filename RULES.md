# Базовые правила крупного проекта

Верхний уровень шаблона архитектуры. Узел и его инструменты — Go stdlib;
стек продукта выбирает проект и фиксирует в своём профиле. Сторонних
зависимостей у узла нет. Правила не зависят
от предметной области и размера команды. Их читает агент перед каждым шагом
и человек, когда принимает работу.

**Схема:** `docs/scheme-rules.svg` — текст в git.
**Обновить:** `go run ./cmd/schemes -write` или
`python verify.py --update-schemes`.

## Как пользоваться

Правила действуют в трёх точках каждого шага:

- **до** — понять цель, границы и источник истины;
- **во время** — не сломать контракт, слои и чужие данные;
- **после** — доказать факт, откатить ошибку, обновить карту.

Если правило мешает скорости — выигрывает правило. Исключение допустимо только
явное, узкое и записанное: что нарушили, почему, когда пересмотреть.

## Десять правил

### 1. Чистый код, имена и уборка

Имя функции — глагол + объект: `CreateUser`, `ParseConfig`, `SendReport`.
Имя переменной — существительное. Пишем читаемый код и убираем за собой:
мёртвый код, комментарии-кладбища, временные файлы и отладочный вывод
удаляются в том же шаге. Старый код, который больше не используется,
не комментируется, а удаляется: история остаётся в репозитории.
Закрытый долг удаляется из `docs/DEBT.md`; ссылка на решение — в
`JOURNAL.md` или `docs/adr/`.

- **Проверка:** имя функции — глагол + объект, имя переменной — существительное; в диффе нет неиспользуемого кода, закомментированных блоков, временных файлов и отладочного вывода; закрытый долг удалён из `docs/DEBT.md`.
- **Цена:** имена-загадки и мусор: через месяц никто не знает, что живо.

### 2. Все новые фичи — в схемах

Каждая новая фича и изменение поведения сначала появляются на схеме плана —
что должно быть, затем в коде, после — на схеме факта — что есть.
Схемы, ADR и журнал меняются тем же шагом; расхождение карты и кода — дефект.

- **Проверка:** до кода есть место фичи на схеме плана; после — она отражена на схеме факта; схемы, ADR и журнал обновлены.
- **Цена:** фича есть в коде, но не на карте; следующий шаг её не видит.

### 3. Тесты под каждую фичу

Под каждую новую фичу — тест: поведение и запреты («список = дерево»,
«данные не теряются», «id не режется»). Тесты лежат по блокам и фичам,
а не одним файлом: правка теста не требует читать тысячи строк.
Тест должен падать, если фича или инвариант сломаны; тест только на
happy path — не тест.

- **Проверка:** у каждой новой фичи есть тест, который падает при её поломке; у каждого инварианта — тест; тесты разбиты по блокам, а не лежат одним файлом.
- **Цена:** фича работает «на глаз», а завтра ломается молча.

### 4. Ноль сторонних зависимостей у узла и инструментов

Узел и его инструменты пишем на Go stdlib: никаких сторонних модулей,
npm, node_modules и обновлений пакетов. Стек продукта — выбор проекта;
шаблон его не диктует и не проверяет Go-модули продукта. ООП — через
структуры, интерфейсы и композицию: инкапсуляция, одна ответственность,
зависимости внутрь. Домен не знает про БД, HTTP и UI.

- **Проверка:** в `go.mod` нет сторонних `require`; сборка с `-mod=readonly`; домен не импортирует инфраструктуру; у структуры или пакета одна ответственность.
- **Цена:** сторонняя зависимость притащила CVE, и продукт нельзя собрать без обновлений.

### 5. Схемы — источник истины

Каждое правило или изменение шаблона отражается на соответствующих схемах
тем же шагом. Схема — не иллюстрация, а источник истины: расхождение схемы
и шаблона — дефект. У сущности один владелец; списки, индексы и деревья —
производные.

- **Проверка:** правило или изменение есть на схеме; у сущности ровно один владелец; второе место — ссылка или кэш с правилом пересборки.
- **Цена:** схема врёт, и следующее изменение строят по ней; данные расходятся.

### 6. Микроблоки и ООП

Каждый блок — маленький, изолированный и с одним контрактом: пакет,
структура, модуль. Бюджет: файл ≤ 400 строк, функция ≤ 80. ООП — база:
инкапсуляция, интерфейсы, композиция. Данные — типизированные структуры,
не map; глобального изменяемого состояния нет, зависимости — через
конструктор или интерфейс. У блока есть короткое описание: что, зачем, как.
Контракт фиксируется до кода; смена контракта — отдельный шаг с миграцией.

- **Проверка:** у блока один контракт и одна причина изменения; файл ≤ 400 строк, функция ≤ 80; нет map-моделей и глобального состояния; есть описание «что/зачем/как»; до кода есть интерфейс/схема; блок тестируется отдельно.
- **Цена:** блоки срослись, и любая правка тянет половину проекта.

### 7. Читать перед записью

Целевой артефакт читается целиком до изменения: файл, схема, конфиг.
Отступ, порядок и соседние строки берутся из него, а не из памяти.
Замена подтверждается проверкой ожидаемого текста.

- **Проверка:** перед правкой открыт нужный блок; после — изменено ровно то, что планировалось.
- **Цена:** правка в чужом месте — код цел, но не тот.

### 8. Пять минут — стоп

Одна причина — один диф. Копия → замена → сборка → откат при ошибке.
Шаг без плана отката не начинается. Если обдумывание идёт больше пяти
минут, прерви его: опиши, что уже сделано и что ещё не сделано, и остановись.
Формат: «Сделано», «Не сделано», «Следующий шаг» — если он нужен.
Дальше — только по новой команде.

- **Проверка:** у шага есть причина и план отката; после пяти минут обдумывания есть запись «сделано / не сделано» и процесс остановлен.
- **Цена:** контекст сгорел, а результата и состояния нет.

### 9. Проверять живо

«Команда выполнена» не равно «работает». Доказательство — живой результат:
журнал, экран, страница, фактическое число записей.

- **Проверка:** результат увиден глазами, а не выведен из кода возврата.
- **Цена:** отчёт зелёный, пользователь видит пустоту.

### 10. Данные и секреты

Опасные операции — в песочнице. Секреты — вне кода и логов.
Бэкап считается сделанным только после проверки восстановления.
Миграции append-only: старые шаги не редактируются и не удаляются;
миграция — только с копией и планом отката.

Логи не смешиваются: тесты пишут в `tests/test.log`, прод-ошибки —
в `var/log/app.log`, `JOURNAL.md` — только решения. Код и тесты
не пишут в `JOURNAL.md`. Каждый поток — не больше 100 КБ на страницу
и не больше 5 страниц.

- **Проверка:** в диффе нет ключей; бэкап восстановлен на копии; шаги миграций не удалены; тестовый и прод-лог раздельны, `JOURNAL.md` не используется как runtime-лог; каждая страница ≤ 100 КБ, страниц ≤ 5.
- **Цена:** данные стёрты, ключи утекли, тестовый шум подменил решения.

## Цикл шага: семь ворот

1. **Понять.** Цель, затронутые файлы и сущности, источник истины, критерий факта.
2. **Спроектировать.** Контракт, ООП-границы, место фичи на схеме плана, влияние на данные.
3. **Изменить.** Минимальный диф, без попутных рефакторингов и «заодно».
4. **Собрать.** Компиляция, линт, типы. Ошибка — откат, а не «потом поправлю».
5. **Проверить.** Тесты на фичу, инварианты, песочница на копии данных.
6. **Доказать.** Живой результат: журнал, экран, фактические данные.
7. **Записать.** Схемы факта и плана, ADR, журнал. Только теперь шаг закрыт.

Ворота не пропускаются. Если проверка не пройдена — шаг не закрыт, даже если код написан.

## Процесс: красный не проходит

Полный процесс — [PROCESS.md](PROCESS.md), схема —
`docs/scheme-process.svg`.
Правила → тест → изменение → verify → деплой только на 0 → ADR/журнал.

`python verify.py` — единственный red gate. Ненулевой код запрещает merge
и деплой; красный — стоп, отчёт «сделано / не сделано», назад в изменение.

## Стоп-сигналы

| Сигнал | Что сделать вместо этого |
| --- | --- |
| Правлю, не прочитав блок | Открыть блок целиком |
| Срез по числу вместо разбора | Разбирать по смыслу |
| Одна сущность в двух местах | Свести к источнику истины |
| «Выполнено» без живого факта | Журнал, экран, данные |
| Нет копии и плана отката | Сначала откат — потом правка |
| Секрет в коде или логе | Вынести в окружение |
| Мёртвый код оставлен про запас | Удалить: история есть в репозитории |
| Фича без теста | Тест на поведение и запреты |
| Схема не обновлена | Карта — тем же шагом |

## Определение готовности

- [ ] `python verify.py` зелёный: сборка, тесты, секреты, drift, размеры, схемы.
- [ ] Тесты на каждую фичу и инварианты зелёные.
- [ ] Живая проверка: журнал, экран, фактические данные.
- [ ] Откат возможен и проверен.
- [ ] Мёртвый код, временные файлы и отладочный вывод удалены.
- [ ] Схемы факта и плана, ADR и журнал обновлены.
- [ ] В диффе нет секретов, мусора и чужих правок.

## Как адаптировать шаблон

- **Стек узла:** Go stdlib для инструментов; продукт — отдельный проект со своим стеком.
- **Инструменты:** Git/CI/Python — вне продукта; SVG-схемы — Go stdlib.
- **Меняется:** предметная область, названия слоёв, команды сборки и тестов, формат схем, место ADR.
- **Не меняется:** десять правил, семь ворот, определение готовности.
- **Профиль проекта:** заполнить `PROJECT.md` под проект; шаблон уже есть.

## Стратегия и улучшения

Правила — первый слой. Видение, дорожная карта и очередь улучшений —
в [STRATEGY.md](STRATEGY.md). Схемы: `docs/scheme-strategy.svg`,
`docs/scheme-roadmap.svg` — текст в git, генерируются Go.

Бюджет шаблона — десять правил: новое правило должно вобрать старое
или доказать, что без него рвётся контур.
