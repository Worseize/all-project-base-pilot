# Журнал решений

Одно решение — одна запись. Формат: дата, версия, решение, почему,
что отвергли, последствия, ссылки.

## 2026-10-26 · 0.9.44 · Колонка «Кому» и onboarding

**Решение:** доска — семь колонок с «Кому»; итоги по разделам; старт
новой сессии — по `docs/TO-AGENTS-ONBOARDING.md`.

**Почему:** владелец должен видеть адресата без открывания репозитория;
новая сессия не должна тащить историю.

**Последствия:** форматтер и тест обновлены; AGENTS содержит строку старта.

## 2026-10-26 · 0.9.43 · Прецеденты в архив

**Решение:** истории правил — в `docs/AGENTS-ARCHIVE.md`; AGENTS.md только
правила, бюджет 14 КБ, проверка `agents-size`.

**Почему:** AGENTS.md переотправляется каждый ход; истории стоили токенов.

**Последствия:** архив заведён, бюджет проверяется тестом.

## 2026-10-26 · 0.9.42 · Колонка # в долгах

**Решение:** сообщение о долгах без колонки `#` не считается отчётом;
`deploy/debt-table.py` всегда печатает шесть колонок.

**Почему:** предыдущий отчёт был без `#`, владелец не смог сопоставить
строки доски.

**Последствия:** правило в AGENTS, тест форматтера; заодно закрыт
D-SITE-SYMLINK (`realpath`).

## 2026-10-26 · 0.9.41 · Доска долгов и закрытие в ответе

**Решение:** `DEBTS.md` — единая доска; каждый ответ с открытым долгом
закрывает хотя бы один живой проверкой; `check_handoffs` видит
`TO-AGENTS-*`.

**Почему:** у агентов был разный формат, а долги жили в голове.

**Последствия:** D-HANDOFFS снят; остались D-MANIFEST-GATE и D-SITE-SYMLINK.

## 2026-10-26 · 0.9.40 · Пересчёт долгов на пробуждении

**Решение:** каждое пробуждение пересчитывает `docs/DEBT.md`; report
содержит `долги: +N / −M / изменено K`.

**Почему:** после письма/решения/чужого коммита реестр обязательств
отставал от реальности.

**Последствия:** три долга аудита зафиксированы явно; закрытие — только
после живой проверки.

## 2026-10-26 · 0.9.39 · Фронт работ в чате

**Решение:** каждый статусный ответ содержит таблицу «Сделано / Не сделано /
Осталось»; «готово» — только при пустом «Не сделано».

**Почему:** владелец и агент должны видеть незакрытый фронт, а не только
успешные пункты.

**Последствия:** правило в `AGENTS.md`, проверка в `tests/test_verify.py`.

## 2026-10-25 · 0.9.38 · Аудит: права, манифест, gate

**Решение:** не трогать `/var/log`; бэкап 0700 root + count; onboarding
валидирует `project.conf`; gate/auto-merge читают run/test/health; `site`
не выходит из проекта.

**Почему:** зелёные тесты скрывали права, неполный restore и обход
манифеста.

**Последствия:** CI проверяет существующий 0755-каталог бэкапа, count
mismatch, traversal; режимы `deploy/*.sh` остаются 100755.

## 2026-10-25 · 0.9.37 · Аудитория и коннектор

**Решение:** файлы агента начинаются с `Аудитория: агент ...`;
`check_handoffs` запрещает маркеры задач владельца. Коннектор проекта
описывает роли/границы/шину/готово; онбординг кладёт его в проект.

**Почему:** агент видел список действий владельца и мог начать «помогать».

**Последствия:** gate проверяет аудиторию; проект получает коннектор.

## 2026-10-25 · 0.9.36 · .env.* guard

**Решение:** `pre-receive` ловит `.env.local`, `.env.production` и подобные;
`.env.example` явно разрешён. CI пушит оба варианта.

**Почему:** `\.env$` пропускал секреты с суффиксом.

**Последствия:** маленький PR из устаревшего #37; без ребейза.

## 2026-10-25 · 0.9.36 · Пояс, таймеры, аудит

**Решение:** `timezone` по умолчанию пустой; `TZ` не пишется без запроса;
cleanup снимает backup-таймеры/каталоги; audit проверяет TZ, apt timers и
осиротевшие backup-таймеры.

**Почему:** проект наследовал UTC вместо пояса хоста; приёмка оставляла
таймеры; аудит не видел выключенных обновлений.

**Последствия:** CI проверяет отсутствие `Environment=TZ=` по умолчанию.

## 2026-10-25 · 0.9.35 · Бэкапы: четыре тихих дефекта

**Решение:** убрать SIGPIPE; проверить exec-бит всех deploy-скриптов;
`check-backups.sh` с порогом 26 ч в selftest/bootstrap; cleanup отключает
backup-таймеры и удаляет `/var/backups/<id>`.

**Почему:** архив >64 КБ ложно считался битым; `100644` даёт `203/EXEC`;
вчерашний снимок не восстанавливает сегодняшние данные; фикстуры
оставляли таймеры и каталоги.

**Последствия:** CI с большим архивом, состаренным снимком и проверкой
отсутствия таймеров/каталогов после cleanup.

## 2026-10-25 · 0.9.33 · Бэкап данных проекта

**Решение:** узел ставит `proj-backup@<id>.timer` при онбординге; снимок
`/var/backups/<id>`, 0700/0600, KEEP 14, проверка restore при установке.

**Почему:** данные проекта оставались без резерва; проект не должен
заводить свой таймер.

**Последствия:** у каждого проекта ежедневный снимок и проверенный restore;
CI-фикстура.

## 2026-10-25 · 0.9.32 · Сверка с packet

**Решение:** state фиксирует `/etc/localtime` и режим `/etc/git-hooks`;
snapshot по умолчанию `/var/backups/<id>`; `site` принимает
`static:<dir>`/`proxy:<port>`.

**Почему:** packet требует эти поля и формат; иначе расход с заданием.

**Последствия:** CI state и snapshot соответствуют packet.

## 2026-10-25 · 0.9.31 · Состояние узла до/после

**Решение:** `state.sh` снимает нормализованное состояние (пути, режимы,
юниты, hooks, ufw, sysctl, TZ, пользователи) и сравнивает; isolation
падает при любом различии. Негатив — `chmod 0755 /srv`.

**Почему:** зелёная приёмка ослабляла хост; это не видел ни один тест.

**Последствия:** побочные эффекты ловятся в CI; `/srv` восстановлен.

## 2026-10-25 · 0.9.30 · /srv после приёмки

**Решение:** cleanup не трогает `/srv`; CI проверяет `711` после очистки.
**Почему:** cleanup ставил `0755`, ослабляя базовый `0711`.
**Последствия:** audit-drift после приёмки чист.

## 2026-10-25 · 0.9.29 · Данные, снимки, откат

**Решение:** данные не в git (гейт и data-guard); снимки tar+sha256 вне
репозитория с retention 7 дней; `snapshot.sh --verify`; `rollback.sh` по
сохранённому sha; три уровня отката в PROCESS.

**Почему:** «данные вне кода» без дисциплины снимков и проверенного отката
не даёт восстановиться; код-откат без sha — догадка.

**Отвергли:** данные в git; непроверенный restore.

**Последствия:** six CI-сценариев; selftest проверяет snapshot.

## 2026-10-25 · 0.9.28 · python3-venv как зависимость узла

**Решение:** HOST перечисляет git/curl/caddy/python3-venv с условиями;
`selftest.sh` проверяет venv и говорит «поставь python3-venv»; CI падает
с тем же текстом, а не skip; `host-baseline` ставит пакет идемпотентно.

**Почему:** `deps/build` на чистом хосте падал с `ensurepip is not
available`, не указывая пакет.

**Последствия:** чистая Ubuntu краснеет на selftest; после установки —
зелёная.

## 2026-10-25 · 0.9.27 · Манифест: run и venv

**Решение:** ключ `run` необязателен, но файл `run` обязан быть
исполняемым; в CI базовый build не требует venv, сценарий venv
пропускается, если `python3 -m venv` недоступен. `HOST.md` отмечает
`python3-venv` как опциональный пакет.

**Почему:** умолчание run разумнее обязательного ключа; venv зависит от
пакета хоста, а не от проекта.

**Последствия:** manifest-тест принимает отсутствие ключа и отклоняет
`run=missing`; `systemctl is-active` проверяется после рестарта.

## 2026-10-25 · 0.9.27 · Манифест проекта

**Решение:** `project.conf` объявляет run/test/health, deps/build/migrate,
site/domains/redirects, port, memory, cpu, timezone. Валидатор отклоняет
неизвестные ключи; deploy выполняет deps→build→migrate, генерирует Caddy
и drop-in TZ/лимитов.

**Почему:** произвольный проект с зависимостями, базой или сайтом иначе
не встанет; узел не знает, что собирать и когда мигрировать.

**Отвергли:** магию по языкам; фиксированные лимиты; ручной Caddy.

**Последствия:** семь CI-сценариев manifest; skeleton содержит
`project.conf`.

## 2026-10-25 · 0.9.26 · Один сторож и фикстуры

**Решение:** проект отдаёт `health` (0/1, одна строка), узел запускает его
от пользователя проекта с таймаутом 30 с, подавляет повторы, шлёт
«восстановлен». Второго процесса-сторожа у проекта нет. Дефекты живого
проекта закрываются только CI-фикстурой; три документа содержат правило.

**Почему:** два сторожа — два канала/токена; проверка, не воспроизводимая
на фикстуре, не готова.

**Отвергли:** отдельный watchdog проекта; алерты из проекта; тесты «на
живом проекте».

**Последствия:** health обязателен, отсутствие — config error; CI гоняет
шесть health-сценариев; `check_fixtures` в гейте.

## 2026-10-25 · 0.9.25 · Выравнивание review

**Решение:** после успешного merge/deploy узел ставит `review` на `main`;
при сбое deploy откатывает `main` и `review` на прежний коммит. Ключ агента
односторонний, fetch невозможен.

**Почему:** иначе следующий push из истории агента — non-fast-forward, а
забрать изменения он не может.

**Отвергли:** давать агенту fetch/clone; ручное выравнивание.

**Последствия:** CI проверяет второй push после auto-merge.

## 2026-10-25 · 0.9.24 · Каталог данных и общий юнит

**Решение:** unit объявляет `StateDirectory=%i`,
`Environment=PROJECT_DATA_DIR=/var/lib/%i`, `ReadWritePaths=/var/lib/%i`;
bootstrap/deploy создают каталог. Cleanup удаляет только экземпляр, общий
`proj@.service` не трогает.

**Почему:** проект писал в код или падал read-only; cleanup ломал другие
проекты.

**Отвергли:** ручные drop-in для данных; удаление общего шаблона в тесте.

**Последствия:** данные вне кода; CI проверяет наличие шаблона после
приёмки.

## 2026-10-25 · 0.9.23 · Контракт данных и режимов

**Решение:** контракт требует `100755` у `run`/`test.sh`, всё состояние под
`PROJECT_DATA_DIR`, чистый клон с пустыми данными; сайт и журналы
описываются в профиле; gate проверяет режим. Skeleton дополнен
данными/сайтом/журналами; CI проверяет негатив `100644`.

**Почему:** живой проект приехал с 100644 и тестами, требующими данные из
репозитория; это ломалось только перепиской.

**Отвергли:** полагаться на Windows-режим; держать данные в чекауте;
конфиг прокси в проекте.

**Последствия:** проект без 100755 отклоняется; данные/сайт/журналы
описаны до приёмки.

## 2026-10-25 · 0.9.22 · Правило остановки

**Решение:** после двух падений одной проверки — стоп и `blocked`-файл,
без третьей попытки. Готово = коммит в `review`, зелёная проверка, файл
приёмки; issue закрывает администратор.

**Почему:** добросовестный цикл «ещё одна правка» дорожает и не помогает,
если две попытки не сдвинули проверку.

**Отвергли:** третью попытку «на всякий случай»; менять проверку; ждать
закрытия issue.

**Последствия:** AGENTS/AGENT-CONTRACT содержат правило; `check_stop_rule`
ловит регресс.

## 2026-10-25 · 0.9.21 · Хук приёма для скелета

**Решение:** gate берёт `test.sh` из `main`, если он есть; иначе trusted
`verify.py`. Protected-пути задаются на проект (`protected-paths`); у
скелета пусты. Allowlist по умолчанию `*`; ограничение — только если
проект делит репозиторий с узлом.

**Почему:** жёсткие node-пути и `app/` ломали проект из скелета; `test.sh`
из pushed tree нельзя считать доверенным.

**Отвергли:** оставлять verify.py обязательным для проекта; hardcode
protected; allowlist app/.

**Последствия:** скелетный push проходит без ручной правки хуков; узел
сохраняет защиту verify.py; CI isolation гоняет скелетный проект.

## 2026-10-25 · 0.9.20 · Скелет проекта и контракт

**Решение:** проект инициализируется из `skeleton/project` (run, PROJECT,
test.sh, .gitignore, README), а не копией шаблона. Контракт агента —
`docs/AGENT-CONTRACT.md`. Gate/auto-merge запускают `test.sh`, если он есть;
иначе — trusted `verify.py`.

**Почему:** копия шаблона приносит Python-проекту Go-инструменты и правила
узла; агент начинает удалять лишнее и ломает gate.

**Отвергли:** оставлять полный шаблон как стартовый репозиторий; требовать
Go от продукта.

**Последствия:** init принимает источник скелета; проект без Go-файлов
проходит gate; контракт задаёт секреты/данные/review.

## 2026-10-25 · 0.9.19 · Auto-merge по метке и allowlist

**Решение:** `proj-auto-merge.timer` раз в 5 минут запускает trusted gate
по `review`; при зелёном результате пишет root-метку, двигает `main`,
доставляет `current` и перезапускает unit. Решение — только по гейту, без
анализа содержимого. Проект меняет только `allowed_paths`; служебные
пути (`verify.py`, `deploy/`, `tests/`, CI) запрещены всегда.

**Почему:** ручной `update-ref` — лишняя кнопка; allowlist ограничивает
последствия, не судя смысл изменений.

**Отвергли:** egress-allowlist; ежедневный дайджест; нейронку в приёмке.

**Последствия:** `pre-receive` отклоняет пути вне allowlist; timer
идемпотентен, при сбое deploy откатывает `main`; журнал
`/var/log/git/auto-merge.log`.

## 2026-10-25 · 0.9.18 · Узел не диктует язык продукта

**Решение:** Go остаётся только языком инструментов узла (`cmd/schemes`,
`cmd/deadcode`). Стек продукта выбирает отдельный проект; шаблон не требует
`stack: go`, продуктовых команд и `examples/minimal-go`.

**Почему:** админ-узел не должен навязывать язык продукту; Go-политика
протекала в правила, профиль и required-файлы.

**Отвергли:** убирать Go-инструменты сейчас; оставлять Go-пример
обязательным; проверять продукт через корневой Go-модуль.

**Последствия:** правило 4 переформулировано; `project.json` без `stack`;
команды только `cmd/*`; Go-проверки применяются к инструментам, а не к
продукту.

## 2026-10-25 · 0.9.17 · Ubuntu 24.04 delivery

**Решение:** bootstrap и `deploy-project.sh` клонируют/обновляют checkout
от имени пользователя проекта через `runuser`; CI isolation и verify
закреплены на `ubuntu-24.04`; ставится `post-receive`, а после
`update-ref` доставка идёт через `deploy-project.sh`.

**Почему:** root-клон на git 2.43 падает на dubious ownership;
`ubuntu-latest` уже не та ОС; без доставки main код остаётся в bare.

**Отвергли:** `git -c safe.directory` для clone; `ubuntu-latest`;
автоматический deploy после update-ref (хуки не запускаются).

**Последствия:** CI ловит target-версию; isolation проверяет, что main
появляется в `current`; post-receive покрывает push-based main.

## 2026-10-25 · 0.9.16 · Один logrotate, проектный drift, доставка main

**Решение:** оставить одно правило `/etc/logrotate.d/proj-logs` (baseline);
`audit-drift` считать проектом только каталог с `repo.git`/`CANARY`;
bootstrap создаёт `/srv/<id>/current`, а `deploy-project.sh` доставляет
принятый main и перезапускает `proj@<id>.service`; unit смотрит в
`current/run`.

**Почему:** два правила ломают logrotate; любой каталог — ложный сирота;
без checkout принятый код негде запускать.

**Отвергли:** per-project ротацию; обход всех каталогов; «деплой вручную
без скрипта».

**Последствия:** одна ротация; drift только по проектам; доставка —
отдельный проверяемый шаг root.

## 2026-10-25 · 0.9.15 · Шаблон — админ-узел, не продукт

**Решение:** шаблон описывает роль админ-узла и приёмки. Продукты —
отдельные проекты. `check_no_product` запрещает `cmd/app`, `app.service`,
`bin/app` и sudoers с перезапуском сервиса; разрешены только инструменты
`cmd/schemes` и `cmd/deadcode`.

**Почему:** если шаблон снова станет приложением, админ-роль и изоляция
размываются; продукт должен жить у своего агента.

**Отвергли:** оставить `app.service` как пример; разрешить продуктовый
sudoers; возвращать `cmd/app`.

**Последствия:** документы профиля переписаны; `host-baseline.sh` и
`docs/HOST.md` добавляют обвязку узла; `audit-drift` проверяет firewall,
jail, journald и logrotate.

## 2026-10-25 · 0.9.14 · CI-приёмка изоляции

**Решение:** добавить `isolation.yml` и `deploy/ci/isolation.sh`, которые
на `ubuntu-latest` создают `proj-a`/`proj-b`, проверяют `git-shell`, seed
`main`, review/force/delete, подмену `verify.py`, canary, sudo, hooksPath,
лог и logrotate, затем убирают за собой.

**Почему:** ручная приёмка на одноразовом хосте не ловит регресс на каждом
PR; CI делает это автоматически.

**Отвергли:** Docker; сторонние зависимости; ручной прогон.

**Последствия:** новая джоба краснеет при возврате `nologin`, отсутствии
`main` или ослаблении gate.

## 2026-10-24 · 0.9.13 · Агент не пишет в issue

**Решение:** агент только читает issues; отчёт — файл
`docs/acceptance/...` и сообщение коммита `(findings#N)`. Отказ — файл
с первой строкой `Отказ: <причина>`, без изменений в коде.

**Почему:** GitHub не разделяет «комментировать» и «закрывать»; кто может
писать, тот может закрыть. Доказательство должно жить в git.

**Отвергли:** комментарии-отчёты; закрытие агентом; молчание при отказе.

**Последствия:** `check_process` требует запрет комментариев;
`check_acceptance` понимает refusal-файлы.

## 2026-10-24 · 0.9.12 · Issue закрывает только conductor

**Решение:** исполнитель не управляет доской. Агент читает issues и
комментарии, правит шаблон, пишет `published: ...` и «готово, жду
проверки». Закрывает issue только `conductor` после проверки.

**Почему:** шаблон нужен на всех проектах, а не только на Go. При этом
изменение команд — не изменение картинки; drift не должен быть ложным.

**Отвергли:** хардкодить Go в gate; заставлять перерисовывать схемы при
каждой правке команд; тащить npm ради не-Go проектов.

**Последствия:** не-Go проект задаёт `stack` и `commands`, фиксирует
исключение правила 4 в ADR. Запрет npm остаётся, пока `forbid_npm`
не выключен явно.

**Ссылки:** [README.md](README.md), [project.json](project.json),
[verify.py](verify.py).

## 2026-10-22 · 0.7.1 · Secret entropy, branch protection, CI-матрица

**Последствия:** gate стал чувствительнее к случайным секретам; branch

## 2026-10-22 · 0.7.0 · Release candidate: профиль, конфиг, lock и тесты

**Решение:** шаблон стал конфигурируемым: `project.json` задаёт стек,
команды, обязательные файлы и схемы; `PROJECT.md` и `FEATURE.md` —
человеческие профили; `verify.py` читает конфиг. Схемы защищены
`docs/schemes.lock.json`, gate проверяется `tests/test_verify.py`,
Go-путь — `examples/minimal-go`.

**Почему:** до этого gate был захардкожен под этот репозиторий, схемы могли
устареть молча, а генераторы зависели от Windows-шрифта. На втором проекте
пришлось бы менять сам gate — это противоречит смыслу шаблона.

**Отвергли:** редактировать `verify.py` под каждый проект; хранить
обязательные ADR по именам; считать наличие PNG достаточной проверкой схем;
тихо откатываться на дефолтный шрифт.

**Последствия:** новый проект заполняет `project.json` и `PROJECT.md`,
не трогая gate. Изменение правил или стратегии требует
`python verify.py --update-schemes`. Branch protection остаётся настройкой
репозитория, а не файлом.

**Ссылки:** [README.md](README.md), [project.json](project.json),
[tests/test_verify.py](tests/test_verify.py), [docs/schemes.lock.json](docs/schemes.lock.json).

## 2026-10-22 · 0.6.7 · Практики из продуктового чек-листа

**Решение:** взяли механику, а не числа: бюджеты «файл ≤ 400 строк,
функция ≤ 80», типизированные структуры вместо map, тесты по блокам,
бэкап с проверкой восстановления, append-only миграции. `verify.py`
проверяет размеры файлов/функций и `gofmt`, когда появится Go-код.

**Почему:** эти практики уменьшают цену ошибки и не зависят от размера
команды. Они проверяемы, поэтому не остаются лозунгами.

**Отвергли:** 900 тестов / 64 группы как KPI; 71% документации как цель;
абсолютные 80/400 без контекста; Python-специфику (ruff, dict-модели) —
её заменили `go vet`, `gofmt` и типизированные структуры.

**Последствия:** правило 6 стало измеримым, правило 10 — про восстановление
и миграции, правило 3 — про разбиение тестов. Числа-ориентиры остаются
сигналом, а не целью.

**Ссылки:** [RULES.md](RULES.md) (правила 3, 6, 10), [PROCESS.md](PROCESS.md),
[STRATEGY.md](STRATEGY.md), [verify.py](verify.py).

## 2026-10-18 · 0.6.2 · Go stdlib вместо JS/Node

**Решение:** продукт пишем на Go, только стандартная библиотека.
Сторонних модулей, npm и `node_modules` нет. ООП — структуры, интерфейсы,
композиция.

**Почему:** npm — транзитивные зависимости, регулярные обновления и CVE,
которые не зависят от нашего кода. Критерий продукта — ноль зависимостей.

**Отвергли:** JS/Node.js; Python stdlib как продуктовый рантайм;
любые сторонние пакеты.

**Последствия:** один статический бинарник; `go.mod` без `require`;
генераторы схем остаются build-time инструментами на Python/Pillow.

**Ссылки:** [docs/adr/0001-zero-dependencies-go.md](docs/adr/0001-zero-dependencies-go.md).

## 2026-10-17 · 0.5 · Десять правил и бюджет

**Решение:** держать ровно десять правил. Новое правило вбирает старое
или отклоняется.

**Почему:** иначе через месяц правил будет сорок, и их перестанут читать.

**Отвергли:** бесконечный список правил без бюджета; правила без проверки.

**Последствия:** каждое новое требование проходит через слияние с существующим
правилом; стратегия стала отдельным слоем, а не одиннадцатым правилом.

**Ссылки:** [RULES.md](RULES.md), [STRATEGY.md](STRATEGY.md).
