# Контракт агента проекта

Этот документ — механический чеклист. Агент проекта приводит свой репозиторий
к нему без переписки с администратором узла.

## Обязано быть в репозитории

| Файл | Проверка |
| --- | --- |
| `run` | исполняемый; единственная точка запуска |
| `PROJECT.md` | разделы: назначение, стек, команды, границы, данные, окружения, исключения |
| `test.sh` | исполняемый; gate запускает его, если он есть |
| `health` | исполняемый; 0 = здоров, 1 = болен; одна строка причины |
| `project.conf` | `ключ=значение`; неизвестный ключ — отказ |
| `.gitignore` | игнорирует артефакты, `.env*`, данные и логи |
| `README.md` | коротко: как запустить и что это |

`run` не привязан к языку. `test.sh` — единственный контракт проверки;
если его нет, узел использует trusted `verify.py` шаблона.

`health` — интерфейс, а не список проверок: узел запускает его раз в минуту
от имени проекта, с таймаутом 30 с. Код 0 — здоров, 1 — болен; одна строка
причины уходит в общий канал. Что внутри — решает проект. Нет `health` —
ошибка конфигурации, а не «здоров».

## Манифест project.conf

`ключ=значение`, только известные ключи:
`run`, `test`, `health`, `build`, `deps`, `migrate`, `site`, `domains`,
`redirects`, `port`, `memory`, `cpu`, `timezone`.

- `deps`, `build`, `migrate` — команды от пользователя проекта; выполняются
  до рестарта, при ошибке деплой падает.
- `run` — необязательный ключ (по умолчанию `run`); сам файл `run`
  обязателен и исполняемый.
- `site=none|static[:dir]|proxy[:port]`; Caddy-блок генерирует узел.
- `timezone`, `memory`, `cpu` применяются через drop-in юнита.
  Пустой `timezone` — наследовать пояс хоста; `TZ=UTC` без запроса не ставится.
- Неизвестный ключ, `site` вне множества или несуществующий `run` — отказ.

## Режим файлов

`run` и `test.sh` обязаны быть `100755` **в git**, не только на диске.
На Windows режим не сохраняется, поэтому проверяй:

```bash
git ls-tree HEAD run test.sh
```

Ожидается `100755` у обоих. `100644` — отказ приёма: служба не стартует.

## Данные и PROJECT_DATA_DIR

Всё состояние проекта — под `PROJECT_DATA_DIR` (его задаёт узел).
`test.sh` должен быть зелёным в чистом клоне с **пустым** каталогом данных:
тесты не требуют `users.json`/`usage.json` из репозитория.
Секреты и данные не попадают в `test.sh`.

## Несколько процессов

`run` — единственная точка запуска; он может поднимать дочерние процессы.
Если процессов несколько и есть общие файлы — блокировки (один писатель или
файловый замок) ответственность проекта. Узел видит один процесс и это не
проверяет.

## Сайт

Если у проекта есть статика, объяви в `PROJECT.md`:
- домены;
- корень статики;
- редиректы (301 и т.п.).

Конфиг обратного прокси делает узел; проект его не правит.

## Секреты

- Имена переменных перечислены в `PROJECT.md`.
- Значения лежат в `/etc/<id>/*.env` у узла, не в репозитории.
- `.gitignore` закрывает `.env`, `.env.*`, `data/`, `*.log`.
- В `test.sh` и `run` нет реальных токенов.

## Данные

- Данные проекта никогда не попадают в git: `.gitignore` закрывает
  `data/`, `.env*`, `*.log`; гейт отклоняет файл состояния в индексе.
- Всё состояние — под `PROJECT_DATA_DIR`; путь задаёт администратор.
- Снимок: `snapshot.sh <id>` (tar + sha256) в `/var/backups/<id>`,
  хранение 7 дней; секреты (`*.env`, `.env*`) в снимок не входят.
- Перед откатом — `snapshot.sh <id> --verify`; непроверенный откат не
  считается откатом.
- Данные бэкапит узел (`proj-backup@<id>.timer`, `/var/backups/<id>`);
  проект отвечает за корректность данных и за то, чтобы всё состояние
  лежало в `PROJECT_DATA_DIR`.
- `deploy/*.sh` — `100755` в git; `100644` даёт `203/EXEC`.
- Бэкап без свежести (26 ч) и читаемого `sha256` считается отсутствующим.
- Проект не пишет в `/etc` и `/srv` вне своего каталога.
- `test.sh` зелёный на пустом `PROJECT_DATA_DIR`.

## Журналы и бюджет

- `stdout`/`stderr` проекта уходят в журнал узла.
- Собственные журналы — внутри `PROJECT_DATA_DIR`, со своей ротацией.
- В системные каталоги писать нельзя.
- Быстрый гейт — до пары минут; полный набор — отдельно.
- В тестах нет сети и настоящих секретов; тесты не пишут в рабочие журналы.

## Push

- Только ветка `review`; `main` двигает правило auto-merge после gate.
- Ключ проекта **односторонний**: только `git push`, без `fetch`/`clone`.
  Состояние забирать не нужно: после merge узел выравнивает `review` на `main`.
- Пути — только из allowlist проекта; служебные файлы узла запрещены.
- Force push и удаление `review` запрещены.

## Остановка

Две попытки на одну и ту же проверку. Если третья тоже была бы нужна —
остановись и оформи `docs/acceptance/<дата>-blocked-<slug>.md`: что
проверял, текст ошибки, что пробовал, чего не хватает. `blocked` — это
полноценный результат, а не провал; issue закрывает conductor.

## Проверка — фикстурами

1. Дефект проекта закрывается тестом в CI шаблона: фикстура → действие →
   ожидаемый результат. Без продукта, без имён, без чужого хоста.
2. В issue запрещены «проверим на реальном проекте», «ждём переезд»,
   «закроем, когда проект запустит».
3. Живой проект — только источник: что сломалось и при каких условиях.
4. Не воспроизводится на фикстуре — сначала переформулировать проверку.

## Запрещено

- править `verify.py`, `deploy/`, `tests/` узла, CI и хуки;
- открывать публичные порты и запускать свои демоны;
- хранить секреты в репозитории;
- копировать инструменты узла в проект.

## Перед push

```bash
./test.sh
git status --short
git diff --check
```

Если `test.sh` зелёный и diff не трогает служебные пути — push в `review`.
Дальше решение принимает auto-merge по метке gate.
