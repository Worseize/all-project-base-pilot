# Процесс: красный не проходит

Версия 0.9.1 · 22.10.2026

Схема: [docs/scheme-process.png](docs/scheme-process.png) ·
Правила: [RULES.md](RULES.md) · Стратегия: [STRATEGY.md](STRATEGY.md)

## Цепочка

**Правила → тест → изменение → verify → деплой только на 0 → журнал.**

Это не ещё одно правило, а процесс, который связывает существующие:
правила задают границы, тест доказывает поведение, verify собирает красный
и зелёный, деплой не проходит на красном, журнал сохраняет решение.

## Шаги

| Шаг | Вход | Выход | Ворота |
| --- | --- | --- | --- |
| Правила | задача | применимые инварианты и исключения | правило 5: изменение на схеме |
| Тест | фича или баг | тест на поведение и запреты | тест падает при поломке |
| Изменение | тест и план | минимальный диф | микроблок, откат готов |
| Verify | диф | 0 или 1 | `python verify.py` |
| Деплой | зелёный verify | работающая версия | красный запрещает деплой |
| Журнал | решение и доказательства | ADR или запись в журнале | решение не потеряно |

## Красный

Если `verify.py` вернул ненулевой код:

1. **Не мержить и не деплоить.**
2. Записать отчёт: **«Сделано», «Не сделано», «Следующий шаг»**.
3. Откатить то, что уже применено, если откат нужен.
4. Вернуться в изменение и починить причину, а не отключить проверку.

Красный — это не «почти готово». Это запрет на деплой.

## Зелёный

Если `verify.py` вернул 0:

1. Задеплоить.
2. Проверить живо: журнал, экран, фактические данные (правило 9).
3. Записать решение в `JOURNAL.md` или `docs/adr/`.
4. Обновить схему факта (правило 5).
5. Только теперь задача закрыта.

## Что проверяет verify

| Проверка | Что ловит |
| --- | --- |
| required files | пропали правила, процесс, журнал или схема |
| no npm artifacts | `package.json`, lock-файлы, `node_modules` |
| go.mod | сторонние `require`/`replace`/`exclude` и `go.sum` |
| secrets | ключи, токены, private keys в текстовых файлах |
| junk | временные и мусорные файлы |
| schemes | PNG отсутствует, пустой или повреждён |
| schemes lock | источники изменились, схемы не перерисованы |
| rules | в `RULES.md` не десять правил, индекс AGENTS.md неполный |
| profile | `PROJECT.md` или `FEATURE.md` без обязательных разделов |
| readme | нет быстрого старта |
| journal | журнал решений пуст или без «почему» |
| adr | нет шаблона, ADR мало или неполные разделы |
| process | процесс не описан |
| ci | выбранный в `project.json` CI-файл отсутствует |
| versions | версия в `project.json` не совпадает с документами |
| go sizes (Go) | файл > 400 строк или функция > 80 |
| gofmt (Go) | файл не отформатирован |
| deadcode (Go) | неиспользуемые unexported func/type/var/const/method; `// deadcode:keep` — исключение |
| commands | build/test/lint/fmt/deadcode из `project.json` |

Запуск:

```bash
python verify.py
```

`verify.py` — инструмент на стандартной библиотеке Python. Продукт остаётся
на Go stdlib: никаких npm и сторонних пакетов.

## CI и branch protection

В репозитории три CI-файла:

- GitHub — [.github/workflows/verify.yml](.github/workflows/verify.yml);
- GitLab — [.gitlab-ci.yml](.gitlab-ci.yml);
- Azure DevOps — [azure-pipelines.yml](azure-pipelines.yml).

`project.json.ci` — список: `["none"]` по умолчанию, либо
`github`/`gitlab`/`azure`. `verify.py` проверяет наличие выбранных файлов;
`none` отключает CI.

Файл workflow не включает branch protection сам по себе. В настройках
репозитория нужно включить защиту основной ветки и потребовать проверку
`verify`. Без этого красный workflow можно смержить. Подробная настройка —
[docs/BRANCH_PROTECTION.md](docs/BRANCH_PROTECTION.md).

## Журнал решений

- `JOURNAL.md` — короткие записи по ходу: что решили, почему, что дальше.
- `docs/adr/` — значимые архитектурные решения: контекст, альтернативы,
  последствия.

Одно решение — одна запись. Запись без альтернатив и последствий —
это не решение, а заголовок.

## Почему это работает на неидеальном коде

Процесс проверяет **наблюдаемые факты**, а не красоту кода: тест красный
или зелёный, verify вернул 0 или 1, живой результат есть или нет, откат
готов или нет. Поэтому даже неидеальный код не проходит дальше красного,
а хороший код не считается готовым без доказательства.

Правило 1 (чистый код) снижает вероятность ошибки. Процесс ловит то,
что правило 1 пропустило.

## Границы

- `verify.py` и генераторы схем — build-time инструменты, не продукт.
- Генераторы используют Pillow; в поставку продукта он не попадает.
- Если ноль зависимостей нужен и для инструментов, их переписывают
  на Go/SVG отдельной задачей.
- Branch protection — настройка репозитория, а не файл в репозитории.
