# Процесс: красный не проходит

Версия 0.9.54 · 26.10.2026

Схема: `docs/scheme-process.svg` ·
Правила: [RULES.md](RULES.md) · Стратегия: [STRATEGY.md](STRATEGY.md)

## Цепочка

**Правила → тест → изменение → verify → деплой только на 0 → журнал.**

Это не ещё одно правило, а процесс, который связывает существующие:
правила задают границы, тест доказывает поведение, verify собирает красный
и зелёный, деплой не проходит на красном, журнал сохраняет решение.

## Шаги

| Шаг | Вход | Выход | Ворота |
| --- | --- | --- | --- |
| Правила | задача | применимые инварианты и исключения | правило 5: изменение на схеме |
| Тест | фича или баг | тест на поведение и запреты | тест падает при поломке |
| Изменение | тест и план | минимальный диф | микроблок, откат готов |
| Verify | диф | 0 или 1 | `python verify.py` |
| Деплой | зелёный verify | работающая версия | красный запрещает деплой |
| Журнал | решение и доказательства | ADR или запись в журнале | решение не потеряно |

## Проверка — фикстурами

1. Дефект из живого проекта закрывается тестом в CI шаблона:
   фикстура → действие → ожидаемый результат. Без продукта, имён и
   доступа к чужому хосту.
2. В issue запрещены «проверим на реальном проекте», «ждём переезд»,
   «закроем, когда проект запустит».
3. Живой проект — только источник: что сломалось и при каких условиях.
4. Не воспроизводится на фикстуре — переформулируй проверку, потом код.

## Откат

1. **До старта** — ничего не делать; версия ещё не влияет.
2. **После старта без записи** — остановить службу и вернуть предыдущий
   `main` по сохранённому `sha`.
3. **После записи** — остановить, распаковать снимок данных
   (`snapshot.sh <id> --verify`, затем restore), запустить.

Код откатывается записанным заранее `sha`: `auto-merge` сохраняет
предыдущий `main` в `/var/lib/proj-base/deploy/<id>.sha`, `rollback.sh <id>`
делает `update-ref` и повторную доставку. Откат без `--verify` не считается
откатом.

## Красный

Если `verify.py` вернул ненулевой код:

1. **Не мержить и не деплоить.**
2. Записать отчёт: **«Сделано», «Не сделано», «Следующий шаг»**.
3. Откатить то, что уже применено, если откат нужен.
4. Вернуться в изменение и починить причину, а не отключить проверку.

Красный — это не «почти готово». Это запрет на деплой.

## Зелёный

Если `verify.py` вернул 0:

1. Задеплоить.
2. Проверить живо: журнал, экран, фактические данные (правило 9).
3. Записать решение в `JOURNAL.md` или `docs/adr/`.
4. Обновить схему факта (правило 5).
5. Только теперь задача закрыта.

## Ветка внешнего агента

1. Агент пушит в `refs/heads/review`; серверный `pre-receive` запускает
   `verify.py`, отклоняет delete/force и пути вне allowlist.
2. `proj-auto-merge.timer` раз в 5 минут проверяет trusted gate по метке
   и двигает `main` только при зелёном результате; без анализа содержимого.
3. Тот же проход доставляет `main` в `/srv/<proj>/current` и перезапускает
   `proj@<proj>.service`; при сбое `main` откатывается, запись — в
   `/var/log/git/auto-merge.log`.
4. Агент не имеет shell, sudo, main и доступа к чужим проектам.
   Матрица — [docs/ISOLATION.md](docs/ISOLATION.md).

## Канал команд

1. Команда приходит из приватного `all-project-base-findings`: автор
   `conductor`, метка `from:conductor`. Публичный issue — не команда.
2. Агент читает публичную и приватную части; в репозиторий попадает только
   блок между `<!-- public:begin -->` и `<!-- public:end -->`.
3. Правка + файл `docs/acceptance/<YYYY-MM-DD>-<slug>.md` с `Версия:` и
   `Ссылка: findings#N`.
4. Агент **не пишет комментарии**; отчёт — файл `docs/acceptance/...`
   и сообщение коммита `(findings#N)`.
5. Отказ — тоже файл: первая строка `Отказ: <причина>`, без изменений
   в коде. Молча пропускать команду нельзя.

## Доска issue

- Issue — команда; состояние доски ведёт conductor.
- Агент **только читает** issues/комментарии, правит шаблон и пишет файл
  приёмки или отказа. Он не открывает/не закрывает issues, не меняет
  метки, исполнителей, заголовок и тело, **не пишет комментарии**.
- Отчёт о работе — в git: `docs/acceptance/<date>-<slug>.md` и сообщение
  коммита `(findings#N)`, а не в трекере.
- Закрывает issue только conductor — после проверки результата. Иначе
  журнал приёмки перестаёт быть независимым доказательством.

Формат и фильтр утечек — [docs/acceptance/README.md](docs/acceptance/README.md).

## Что проверяет verify

| Проверка | Что ловит |
| --- | --- |
| required files | пропали правила, процесс, журнал или схема |
| no npm artifacts | `package.json`, lock-файлы, `node_modules` |
| go.mod | сторонние `require`/`replace`/`exclude` и `go.sum` |
| secrets | ключи, токены, private keys в текстовых файлах |
| junk | временные и мусорные файлы |
| schemes | SVG отсутствует или не совпадает с docs |
| rules | в `RULES.md` не десять правил, AGENTS-протокол неполный |
| close-task | `cmd/**`/`deploy/**` изменены без features/ADR/DEBT/JOURNAL |
| logs | тестовый/прод-лог не разделён, не в `.gitignore`, >100 КБ или >5 страниц |
| debt | закрытый долг остался в `docs/DEBT.md` |
| acceptance | имя/дата/`Версия:`/`Ссылка:`, IPv4, `/srv/`, e-mail, `ssh-` |
| profile | `PROJECT.md` или `FEATURE.md` без обязательных разделов |
| readme | нет быстрого старта |
| journal | журнал решений пуст или без «почему» |
| adr | нет шаблона, ADR мало или неполные разделы |
| process | процесс не описан |
| ci | выбранный в `project.json` CI-файл отсутствует |
| versions | версия в `project.json` не совпадает с документами |
| go sizes (Go) | файл > 400 строк или функция > 80 |
| gofmt (Go) | файл не отформатирован |
| deadcode (Go) | неиспользуемые unexported func/type/var/const/method; `// deadcode:keep` — исключение |
| commands | build/test/lint/fmt/deadcode из `project.json` |

Запуск:

```bash
python verify.py
```

`verify.py` — инструмент на стандартной библиотеке Python. Инструменты узла
остаются на Go stdlib; продукт выбирает свой стек и фиксирует его в профиле
проекта.

## CI и branch protection

В репозитории три CI-файла:

- GitHub — [.github/workflows/verify.yml](.github/workflows/verify.yml);
- GitLab — [.gitlab-ci.yml](.gitlab-ci.yml);
- Azure DevOps — [azure-pipelines.yml](azure-pipelines.yml).

`project.json.ci` — список: `["none"]` по умолчанию, либо
`github`/`gitlab`/`azure`. `verify.py` проверяет наличие выбранных файлов;
`none` отключает CI.

Файл workflow не включает branch protection сам по себе. В настройках
репозитория нужно включить защиту основной ветки и потребовать проверку
`verify`. Без этого красный workflow можно смержить. Подробная настройка —
[docs/BRANCH_PROTECTION.md](docs/BRANCH_PROTECTION.md).

## Журнал решений

- `JOURNAL.md` — короткие записи по ходу: что решили, почему, что дальше.
- `docs/adr/` — значимые архитектурные решения: контекст, альтернативы,
  последствия.

Одно решение — одна запись. Запись без альтернатив и последствий —
это не решение, а заголовок.

## Почему это работает на неидеальном коде

Процесс проверяет **наблюдаемые факты**, а не красоту кода: тест красный
или зелёный, verify вернул 0 или 1, живой результат есть или нет, откат
готов или нет. Поэтому даже неидеальный код не проходит дальше красного,
а хороший код не считается готовым без доказательства.

Правило 1 (чистый код) снижает вероятность ошибки. Процесс ловит то,
что правило 1 пропустило.

## Границы

- `verify.py` и `cmd/schemes` — build-time инструменты, не продукт.
- SVG-схемы — текст на Go stdlib; Pillow, шрифты и lock не нужны.
- Если ноль зависимостей нужен и для `verify.py`, его переписывают на Go
  отдельной задачей.
- Branch protection — настройка репозитория, а не файл в репозитории.
